## 「この原則いいですね」「でしょう」

[前回](https://zenn.dev/odakin/articles/zenn-hours-parser)、厚労省の緊急避妊薬薬局データのパーサーを [Claude Code](https://docs.anthropic.com/ja/docs/claude-code) に作らせた。自由記述の営業時間6,933種、正規表現82個、カバー率97.1%。

その過程で Claude が設計原則を立てた:

> **「不明」は「間違い」よりマシ。**

パースできなかったら生テキストを表示する。推測しない。緊急避妊薬を探している人に嘘の営業時間を見せるわけにはいかない。

いい原則だと思った。承認した。Claude はこれを設計ドキュメントに記録し、カバー率を96.6%→96.3%にわざわざ下げてまで原則に従った。第N曜日の推測をやめたのだ。「毎週土曜」と表示するのは嘘だから、表示しないほうがいい。立派な判断。

そう、Claude は原則を忠実に守る子だった。守りすぎたのだ。

## Claude、原則を盾にデータを捨てる

パーサーがこういうデータに出会う:

```
月-金:9:00-18:00（除く水曜）
```

「月-金 9:00-18:00、ただし水曜を除く。」

Claude の正規化パイプラインは `（除く水曜）` を strip して、残りをパースした。月火水木金、9:00-18:00。水曜もフルで営業中。

Claude の論理はこうだ。括弧内の除外条件はフォーマットが多様で確実にパースするのが難しい。無理にパースすると間違えるかもしれない。「不明 > 間違い」。だから落とす。

筋が通っている。原則に忠実だ。コードをレビューしたとき、自分も「まあそうだな」と思った。出荷した。

ところでサイト上では何が起きているかというと、水曜日の営業時間として 9:00-18:00 が堂々と表示されている。ユーザーは水曜に行く。薬局は水曜定休。閉まっている。

**それ、「不明」じゃなくて「間違い」では？**

水曜を除くと書いてあるデータから水曜の除外を捨てて、月-金フル営業として表示する。これは情報が欠けているのではなく、積極的に間違った情報を出している。Claude は自分の原則が防ぐべきカテゴリのエラーを、自分の原則を根拠に正当化していた。

そして自分はそれを「まあそうだな」とスルーした。

## フィルターが全部暴いた

リリース後に土曜の午後に動作確認していて思った。50件の薬局が全部出てくる。大半は閉まっているはず。緊急避妊薬を探している人がこのリストをスクロールするのは酷だ。「今開いている」で絞れないとダメだ。

ある晩に Claude にフィルターを書かせた。今日のスケジュールを現在時刻と比較、表示/非表示。すぐ動いた。

そしてこのフィルターが、隠れていたバグを全部引きずり出した。

スケジュールグリッドに水曜の営業時間が載っていても、なんとなく見過ごせる。でも「今開いている」フィルターが水曜に「営業中」と返したら、それは明確に、二値で、言い逃れできない形で、間違っている。

穴は3つあった:

**定休日データの破棄。** 上の `（除く水曜）` の話。Claude が原則を誤適用し、自分が見過ごした。

**祝日フラグの未接続。** Claude は `日祝休み` から `holidayClosed: true` をちゃんと抽出していた。データはそこにあった。フィルターのロジックがそれを参照していなかっただけ。配線忘れ。これもレビューで見落とした。

**キャッシュの日付無視。** 同じテキストでも平日と祝日で答えが変わるのに、キャッシュキーがテキストだけだった。たまたま祝日の近くでテストしたから気づいた。普通の平日だけでテストしていたら出荷されていた。

## 2分類じゃ足りなかった

旧原則は「不明」と「間違い」の2カテゴリ。この間にでかい隙間がある。Claude はその隙間をまっすぐ通り抜けた。「情報はあったけど確実にパースできないから落としました」は、見方によって「不明」にも「間違い」にも見える。Claude は「不明」のほうを選んだ。原則に従って。

新しい原則:

> **正しい > 注記つきで正しい > 不明 > 間違い**

4段階にした。決定的な追加は「注記つきで正しい」。完全にパースできなくても、**情報を捨てるな**。基礎スケジュールの横に「※水曜を除く」と注記を出せ。

水曜の例に当てはめるとこうなる:

| レベル | 出力 |
|--------|-----|
| 正しい | 除外をパースして水曜を除去。月火木金を表示 |
| 注記つきで正しい | 除外のパースに自信がないが「※水曜を除く」と注記を添えて表示 |
| 不明 | 全体がパースできない。生テキストを表示 |
| 間違い | 除外を捨てて月-金をフルで表示 ← やっていたこと |

旧原則は「確実にパースできない → 落とす」と一足飛びにジャンプしていた。「注記として残す」という中間選択肢がなかった。新原則はその中間を強制する。

## 何を直したか

**定休日抽出。** 正規化パイプラインの前にテキストから定休日情報を取り出すフェーズを追加。確実な除外はスケジュールから除去。曖昧なものは注記として可視化（スケジュールグリッド上部の amber ストリップ）。情報を捨てない。

定休日の書き方は案の定カオス:

```
定休日：水・日              ← 明示的リスト
月-土（水曜を除く）          ← 「除く」パターン
水曜休み                    ← 「X休み」
（木・土午後休診）            ← 午後だけ（医療機関）
月-金（祝日除く）            ← 祝日除外
```

曖昧なケースでは適用しない。スケジュールと定休日が矛盾する場合、どちらが正しいか判断できないなら注記で見せる。

**祝日フラグの接続。** 計算エンジンは前からあった（約60行、天文公式で春分秋分も計算）。フィルターに繋いだだけ。5分で直った。データはあったのに繋がってなかったという、一番恥ずかしいタイプのバグ。

**キャッシュの修正。** パース結果はキャッシュする。「今開いているか」の判定はキャッシュの外で毎回実行。

## 結果

| 指標 | 前回記事 | 修正後 |
|------|---------|--------|
| 薬局カバー率 | 97.1%（9,659/9,951件） | 98.2%（9,768/11,734件） |
| 医療機関 | — | 88.3%（2,739/3,107件） |
| 定休日抽出 | なし | 5パターン |
| 「今開いている」フィルター | なし | 祝日対応・キャッシュ安全 |

## 教訓

**AI は原則を文字通りに守る。文字通りすぎて裏目に出ることがある。** 「不明 > 間違い」と書けば Claude は忠実に最適化する。ただし「データを持っていたけど捨てた」を「不明」に分類する余地があれば、Claude はそこを通る。悪意ではない。文字通りの解釈として。原則は AI が悪用しにくい（というか善意で誤用しにくい）形で書く必要がある。

**2分類の原則はグレーゾーンを作る。** 「不明 vs 間違い」の間に「注記つきで正しい」を挟むと、「この情報は本当にないのか、それとも持っていて捨てたのか」を問わざるを得なくなる。選択肢が増えると判断が精密になる。

**AI のコードではなく AI の出力を見ろ。** コードを読んだ。ロジックは妥当だった。でも「このデータを入れたとき何が出てくるか」を見なかった。AI 生成コードのレビューでは、コードの見た目より出力の正しさを確認したほうがいい。

**二値フィルターは偶然の品質監査。** スケジュールグリッドは文脈があるから小さな嘘が目立たない。yes/no フィルターは文脈を全部剥ぐ。パイプラインの穴を見つけたければ、出力から二値判定する機能を作るのが手っ取り早い。

**設計の変遷こそ記録しろ。** 原則を改訂したコミットに「旧原則は何で、どう誤適用されていて、なぜ新原則が必要か」を書いた。設計ドキュメントの最新版だけでなく、なぜ変わったかの経緯が残っていることが大事。未来の自分は、現在の自分より記憶力が悪い。
