## 正しかったはずの原則

[前回](https://zenn.dev/odakin/articles/zenn-hours-parser)、厚労省の緊急避妊薬薬局データのパーサーを作った。自由記述の営業時間6,933種、正規表現82個、カバー率97.1%。そのとき立てた設計原則:

> **「不明」は「間違い」よりマシ。**

パースできなかったら生テキストを表示する。推測しない。緊急避妊薬を探している人に嘘の営業時間を見せるくらいなら、「わからない」のほうが安全。

この原則にはかなり自信があった。カバー率を96.6%→96.3%に意図的に下げたコミットが最も重要な修正だった、とまで書いた。第N曜日の推測をやめたから。「毎週土曜」と表示するのは嘘だから、表示しないほうがいい。

原則は正しかった。適用の仕方が間違っていた。

## 何を間違えたか

パーサーがこういうデータに出会う:

```
月-金:9:00-18:00（除く水曜）
```

「月曜から金曜 9:00-18:00（水曜を除く）」。

正規化パイプラインは括弧内の `（除く水曜）` を strip して、残りをパースする。月火水木金、全部 9:00-18:00。水曜が出力に含まれている。

これを「不明」に分類した。除外情報は失われたが、基礎スケジュールは保持されている。「不明 > 間違い」だから、これでいい。

本当にそうか？

サイト上で水曜の営業時間として 9:00-18:00 が表示されている。ユーザーはそれを見て水曜に行く。薬局は水曜定休。閉まっている。

**これは「不明」じゃない。「間違い」だ。** 水曜を除くと書いてあるデータから水曜の除外を捨てて、月-金がフルで営業しているかのように表示している。自分の原則が防ぐべきカテゴリのエラーを、自分の原則を根拠に正当化していた。

## 気づいたきっかけ

リリース後、土曜の午後に動作確認していた。50件の薬局が全部表示される。緊急避妊薬を探している人にとって、閉まっている薬局を1件ずつスクロールするのはつらい。「今開いている」フィルターが要る。

ある晩に書いた。今日のスケジュールを見て、現在時刻と比較、表示/非表示。すぐ動いた。

そしてフィルターが、隠れていたバグを表面化させた。

スケジュールグリッドに水曜が載っていても、ユーザーは気づくかもしれないし気づかないかもしれない。でも「今開いている」フィルターで水曜に「営業中」と表示されたら、それは明確に、二値で、間違っている。フィルターはパーサーの穴を拡大鏡にかけた。

穴は3つあった:

**1. 定休日データを捨てていた。** 上の `（除く水曜）` の例。これが設計上の間違い。

**2. 祝日フラグを繋いでいなかった。** パーサーは `日祝休み` から `holidayClosed: true` を抽出済みだった。フィルターがそれを参照していなかった。祝日の月曜に「営業中」。データはあった。配線がなかった。

**3. キャッシュが日付を知らなかった。** 同じテキストでも平日と祝日で答えが変わる。キャッシュキーがテキストだけだったので、平日の答えを祝日にも返した。

2と3は実装ミス。1が設計ミス — 原則そのものが誤った安心感を与えていたケース。

## 修正: 2分類では足りなかった

旧原則は「不明」と「間違い」の2分類。これだと、情報を捨てて不完全な表示をしているのに「不明」に分類できてしまう。

新しい原則:

> **正しい > 注記つきで正しい > 不明 > 間違い**

4段階にした。決定的な違い: **「不明」は本当に情報がないときだけ**。情報を持っていたのに捨てて、残りを完全なものとして表示する — それは「不明」じゃなくて「間違い」。

水曜の例に適用:

- **正しい:** `月-金（除く水曜）` をパースして水曜を除去、月火木金を表示
- **注記つきで正しい:** 除外を確実にパースできないが、スケジュールに「※水曜を除く」と注記を添えて表示
- **不明:** 全体がパースできない。生テキストを表示
- **間違い:** 除外を捨てて月-金を通常営業として表示 ← やっていたこと

修正では正規化パイプラインの前に定休日を抽出するフェーズを追加した。確実に解釈できる除外はスケジュールから除去。曖昧なものは注記として可視化（スケジュールグリッド上部の amber ストリップ）。捨てない。

定休日の書き方は5パターン:

```
定休日：水・日              ← 明示的リスト
月-土（水曜を除く）          ← 「除く」
水曜休み                    ← 「X休み」
（木・土午後休診）            ← 午後だけ（医療機関）
月-金（祝日除く）            ← 祝日除外
```

曖昧なケース（スケジュールと定休日が矛盾する場合など）では適用しない。判断できないなら、注記として見せる。

祝日: 計算エンジンは前からあった（約60行、天文公式で春分秋分も計算）。フィルターに繋いだ。

キャッシュ: パース結果はキャッシュする。「今開いているか」の判定はキャッシュの外で毎回実行。

## 結果

| 指標 | 前回記事 | 修正後 |
|------|---------|--------|
| 薬局カバー率 | 97.1%（9,659/9,951件） | 98.2%（9,768/11,734件） |
| 医療機関 | — | 88.3%（2,739/3,107件） |
| 定休日抽出 | なし | 5パターン |
| 「今開いている」フィルター | なし | 祝日対応・キャッシュ安全 |

## 教訓

**2分類の原則はエラーを隠す。** 「不明 vs 間違い」はきれいに聞こえるが、「情報を持っていたのに捨てた結果の不完全な表示」を「不明」に分類できてしまう。「注記つきで正しい」を間に挟むと、「本当に情報がないのか、持っていて捨てたのか」を問わざるを得なくなる。

**原則は機能追加を生き延びないといけない。** もとの原則はパーサーの表示モード用に作った。生テキスト表示というフォールバックがあるから「不明」が安全だった。「今開いている」フィルターにはフォールバックがない。用途が変わったら原則を再検討すべきだった。

**二値フィルターは偶然の監査になる。** スケジュールグリッドは文脈があるから小さな不正確さを許容できる。yes/no フィルターは文脈を剥ぎ取る。すべての穴が誤答になる。データパイプラインの穴を見つけたければ、出力から二値判定する機能を作ればいい。

**設計の変遷を記録しろ。** 原則を改訂したコミットには「旧原則は何で、どう誤適用されていて、なぜ新原則が必要か」を書いた。未来の自分（と共同作業者）が「なぜこのルールがこうなっているか」を追える。設計ドキュメントは最新版だけでなく、変遷の理由が残っていることが大事。
