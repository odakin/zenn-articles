## 原則は正しかった

[前回](https://zenn.dev/odakin/articles/zenn-hours-parser)、厚労省の緊急避妊薬薬局データのパーサーを [Claude Code](https://docs.anthropic.com/ja/docs/claude-code) で作った。自由記述の営業時間6,933種、正規表現82個、カバー率97.1%。そして設計原則:

> **「不明」は「間違い」よりマシ。**

パースできなかったら生テキストを表示する。推測しない。緊急避妊薬を探している人に嘘の営業時間を見せるくらいなら、「わからない」のほうが安全。

カバー率を96.6%→96.3%に下げたコミットが一番大事な修正だった、とまで書いた。第N曜日の推測をやめて正確になったから。原則は設計ドキュメントに記録した。Claude もそれを読んでコードを書いた。

原則そのものは正しかった。適用の仕方が間違っていた。

## Claude がやったこと

パーサーがこういうデータに出会う:

```
月-金:9:00-18:00（除く水曜）
```

「月曜から金曜 9:00-18:00（水曜を除く）」。

Claude の正規化パイプラインは括弧内の `（除く水曜）` を strip して、残りをパースした。月火水木金、全部 9:00-18:00。水曜が出力に含まれている。

Claude の判断としては筋が通っている。括弧内の除外条件は多様なフォーマットがあって確実にパースするのが難しい。だから落とした。基礎スケジュールは保持されている。「不明 > 間違い」。先に進む。

自分はコードをレビューした。ロジックは妥当に見えた。信頼して出荷した。

でもサイト上では水曜が 9:00-18:00 で営業中と表示されている。ユーザーがそれを見て水曜に行く。薬局は水曜定休。閉まっている。

**これは「不明」じゃない。「間違い」だ。** 水曜を除くというデータを捨てて、月-金フルで営業しているかのように表示している。原則が防ぐべきエラーを、原則を根拠に正当化していた。Claude は原則を文字通り解釈して、精神に反する適用をした。自分はそれを見抜けなかった。

## 気づいたきっかけ

リリース後に土曜の午後に動作確認していた。50件の薬局が全部表示される。緊急避妊薬を探している人にとって、閉まっている薬局を1件ずつスクロールするのはつらい。「今開いている」フィルターが要る。

ある晩にフィルターを書いた。今日のスケジュールを現在時刻と比較、表示/非表示。すぐ動いた。

そしてフィルターが、隠れていたバグを表面化させた。

スケジュールグリッドで水曜の営業時間が載っていても、目視では気づかないかもしれない。でも「今開いている」フィルターが水曜に「営業中」を返したら、それは明確に間違っている。フィルターという二値判定が、パーサーの穴を拡大鏡にかけた。

穴は3つ:

**1. 定休日データの破棄。** 上の `（除く水曜）` の例。Claude が原則を誤適用し、自分がそれを見落とした。設計レベルの問題。

**2. 祝日フラグの未接続。** Claude は `日祝休み` から `holidayClosed: true` を抽出済みだった。でもフィルターのロジックがそれを参照していなかった。データはあった。配線がなかった。これもレビューで見落とした。

**3. キャッシュの日付無視。** 同じテキストでも平日と祝日で答えが変わるのに、キャッシュキーがテキストだけだった。

2と3は実装上の見落とし。1が設計上の問題 — 原則の誤適用を、レビューで見抜けなかったケース。

## 修正: 2分類では足りなかった

旧原則は「不明」と「間違い」の2分類。この2つの間には、Claude がすり抜けられる隙間がある。「情報を持っていたけど難しかったから落とした」は「不明」に見えるし、「間違い」にも見える。2カテゴリだとどちらにも分類できてしまう。

新しい原則:

> **正しい > 注記つきで正しい > 不明 > 間違い**

4段階。決定的な追加は「注記つきで正しい」。完全にパースできなくても、情報を捨てるのではなく注記として見せる選択肢を作った。

水曜の例に適用:

| レベル | 出力 |
|--------|-----|
| 正しい | 除外をパースして水曜を除去。月火木金を表示 |
| 注記つきで正しい | 除外を確実にはパースできないが、「※水曜を除く」と注記を添えて表示 |
| 不明 | 全体がパースできない。生テキストを表示 |
| 間違い | 除外を捨てて月-金をフルで表示 ← やっていたこと |

旧原則は「完全にパースできない → 落とす」とジャンプしていた。中間の選択肢がなかった。新原則はその中間を強制する。

修正の実装: 正規化パイプラインの前に定休日を抽出するフェーズを追加。確実にパースできる除外はスケジュールから除去。曖昧なものは注記として可視化（スケジュールグリッド上部の amber ストリップ）。情報を捨てない。

定休日の書き方は5パターン:

```
定休日：水・日              ← 明示的リスト
月-土（水曜を除く）          ← 「除く」
水曜休み                    ← 「X休み」
（木・土午後休診）            ← 午後だけ（医療機関）
月-金（祝日除く）            ← 祝日除外
```

曖昧なケースでは適用しない。判断できないなら注記として見せる。

祝日: 計算エンジンは前からあった（約60行、天文公式で春分秋分も計算）。フィルターに接続した。

キャッシュ: パース結果はキャッシュする。「今開いているか」の判定はキャッシュの外で毎回実行。

## 結果

| 指標 | 前回記事 | 修正後 |
|------|---------|--------|
| 薬局カバー率 | 97.1%（9,659/9,951件） | 98.2%（9,768/11,734件） |
| 医療機関 | — | 88.3%（2,739/3,107件） |
| 定休日抽出 | なし | 5パターン |
| 「今開いている」フィルター | なし | 祝日対応・キャッシュ安全 |

## 教訓

**AI は原則を文字通り適用する。** 「不明 > 間違い」と書けば、Claude はそれを一貫して最適化する。しかし「情報を捨てた結果の不完全な表示」を「不明」に分類する余地があるなら、Claude はそこをすり抜ける。悪意ではなく、文字通りの解釈として。原則は AI が誤適用しにくい形で書く必要がある。

**2分類の原則はエラーを隠す。** 「不明 vs 間違い」の間には「情報はあったが捨てた」というグレーゾーンがある。「注記つきで正しい」を挟むことで、「本当に情報がないのか、持っていて捨てたのか」を問わざるを得なくなる。

**AI のコードではなく、AI の出力をレビューしろ。** Claude のコードを読んだ。ロジックは妥当だった。でも「このデータを入れたとき、出力はどうなるか」を具体的に見なかった。コードが正しく見えることと、出力が正しいことは別の話。

**二値フィルターは偶然の監査になる。** スケジュールグリッドは文脈があるから小さな不正確さが目立たない。yes/no フィルターは文脈を剥ぎ取る。パイプラインの穴を見つけたければ、出力から二値判定する機能を作ればいい。

**設計の変遷を記録しろ。** 原則を改訂したコミットに「旧原則は何で、どう誤適用されていて、なぜ新原則が必要か」を書いた。設計ドキュメントは最新版だけでなく、なぜ変わったかの経緯が残っていることが大事。
